# Эпоха 16 — Параллельный glossary extract

## Цель
Поддержать glossary extract --concurrency N с несколькими запросами к модели одновременно, сохранив канон, порядок записей и оплаченные ответы при resume.

## Вход / выход
Те же файлы и флаги extract плюс --concurrency 1–8. Translator:ExtractMaxConcurrency — отдельная настройка, default 1 для совместимости прежнего последовательного режима. CLI перекрывает настройку. Translate:MaxConcurrency и его поведение не менять.

## В скоупе
- Перед LLM проверять диапазон 1–8. --list-pairs нельзя сочетать с явным --concurrency.
- Prefix остаётся один на запуск, как в текущей реализации: правила + исходный merge-into / пустой корпус. Результаты не подмешивать в prefix.
- Первый оставшийся запрос выполнить отдельно для прогрева кеша, далее ограниченный пул до N. Ретраи занимают слот до завершения.
- Все ответы сливать в исходном порядке плана (пара / фрагмент), независимо от порядка завершения запросов. Canonical ru по-прежнему не затирается.
- Один писатель result/out/state; IRunProgress сериализует общий RunProgressReporter, RecordResponse и StepEnd используют конкретный label. ETA учитывает ширину пула.
- ExtractCheckpointState получает необязательный PendingOutputs: label -> полный Content успешного ответа, который ещё не слит из-за незавершённого предыдущего шага.
- Сразу после успешной генерации сохранить PendingOutputs в state. Затем последовательно сливать доступные ответы с начала remaining, убирать их из PendingOutputs и отмечать CompletedSteps, обновляя --out и state после каждого слияния.
- PendingOutputs — готовые оплаченные ответы: resume не вызывает для них LLM. После восстановления предыдущего шага они сливаются в порядке плана. Старые state без поля остаются совместимыми.
- При конечной ошибке остановить запуск новых запросов; уже запущенные дождаться и сохранить успешные ответы, после чего пробросить первую ошибку. Упавший шаг не skip/done.
- При внешней отмене LLM получает ct; уже вернувшийся успешный ответ и его checkpoint сохранять без отмены посреди записи. Дождаться текущих задач перед выходом.
- N можно менять при resume: состав и границы плана не меняются. Existing resume fingerprint остаётся прежним.
- Empty/malformed model Markdown сохраняет прежний warning/skip merge и Completed поведение.
- --pairs / --max-pairs, нарезка пар, формат Markdown-словаря и транспорт без изменений.

## Вне скоупа
Новые пакеты/проекты, автоподбор параллельности по балансу, изменения translate, рост prefix, новая модель, платная проверка книги.

## Контракты
IGlossaryExtractService.ExtractAsync(..., workDir=null, resume=false, concurrency=null)
ExtractRunContext.Concurrency // int?
TranslatorOptions.ExtractMaxConcurrency // int, default 1
ExtractCheckpointState.PendingOutputs // Dictionary<string,string>, default empty

## Критерии приёмки
- CLI принимает --concurrency; 0/9 и --list-pairs + --concurrency дают отказ до LLM.
- После прогрева N=2: следующие запросы стартуют до завершения любого; in-flight никогда >N.
- N=1 / default: последовательная обработка.
- Обратный порядок завершения не меняет canonical ru и порядок словаря.
- При провале одного параллельного шага успешные последующие ответы сохранены, новые запросы не запускаются.
- Resume не повторяет Done и PendingOutputs, завершает пропущенный шаг и сливает готовый хвост; изменение N разрешено.
- Параллельные записи не рвут state/out; при отмене активные задачи завершены до возврата.
- Все тесты без сети; сборка/тесты через Roslyn MCP. После реализации сверка в docs/fixes/16-extract-concurrency.md.

## Риски
Буфер готовых ответов может расти, если ранний запрос долго ждёт. --out обновляется по порядку, более поздние готовые ответы до этого лежат в state. Нельзя удалять work-dir до завершения или resume, иначе оплаченный хвост потеряется.
Больше in-flight требует больше доступного баланса и может давать 429/402. Упавший запрос не означает, что другой провайдер уже прекратил работу; текущие задачи дожидаются результата.
