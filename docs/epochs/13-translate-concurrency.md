# Эпоха 13 — Параллельный translate

## Цель

Долгий `translate` не ждёт одну главу, пока шлюз свободен. Несколько независимых чанков идут в модель одновременно. Extract, префикс и провайдер не трогать.

## Вход / выход

**Вход:** те же флаги `translate`, плюс опциональный `--concurrency`. `Translator:MaxConcurrency` в json / Local.

**Выход:** тот же EPUB, work-dir и чекпоинты, что в эпохе 03. Бар на stderr: одна область; подпись — in-flight id чанков.

## В скоупе

- `Translator:MaxConcurrency`: дефолт **2**, допустимо **1–8**. Меньше 1 или больше 8 — ошибка до LLM, в тексте диапазон.
- CLI `translate --concurrency N`: перекрывает Options на один запуск. Тот же диапазон 1–8. Без флага — значение Options.
- Оставшиеся чанки (`pending` / `failed`; `done` по-прежнему не зовут LLM): первый — **один**, затем пул до `MaxConcurrency` in-flight. Прогрев кеша префикса: параллельный старт всех чанков даёт несколько cache-write дорогого словаря.
- Ретраи чанка, валидатор, `failed` после исчерпания — как в 03 / [fixes/03-resume-failed.md](../fixes/03-resume-failed.md). Слот пула не отпускать, пока ретраи этого чанка не закончились.
- Запись `state.json` и `candidates.md` — не параллельно (один писатель). Файлы `chunks/{id}.*` можно писать по своим id одновременно.
- Вызовы `IRunProgress` сериализовать в Core: Spectre/эпоха 11 остаются однопоточными. `StepBegin`: текущие in-flight id через запятую, порядок стабильный (как в плане чанков).
- ETA стены: среднее длительности **завершённого** шага × `ceil(осталось / текущая_ширина)`, не «все шаги подряд». Пока идёт прогрев (первый чанк), ширина = 1; дальше — `MaxConcurrency` (или меньше, если чанков осталось меньше).
- `HttpClient` `llm` не менять. `402` по-прежнему не ретраимый.

## Вне скоупа

- параллельный `glossary extract` (префикс растёт после пары)
- менять `ILlmProvider` / streaming / batch API
- файл стоимости / прайс в рублях
- новый пакет, четвёртый проект, keyed DI
- расширять `IRunProgress` новыми методами, если сериализация вызовов достаточна
- показывать ретраи 2/3 как отдельные шаги бара
- автоподбор N по балансу Provod

## Контракты

```
ai-translator translate --input <epub> --glossary <md> --out <epub>
            [--model <id>] [--work-dir <path>] [--resume]
            [--chapters <n>|<from>-<to>]
            [--concurrency <1-8>]
```

```
TranslatorOptions.MaxConcurrency   // int, default 2, range 1..8
```

`--concurrency` есть только у `translate`. Extract флаг не получает.

Поведение пула — деталь реализации; контракт: не больше N одновременных `ILlmProvider.CompleteAsync` после прогрева; прогрев = первый оставшийся чанк завершил `CompleteAsync` (успех или исчерпание ретраев), затем остальные.

## Критерии приёмки

- `MaxConcurrency: 2`, два оставшихся чанка после прогрева: оба `CompleteAsync` стартовали до завершения любого из них (мок с ручным сигналом)
- `MaxConcurrency: 1`: второй `CompleteAsync` не стартует, пока не вернулся первый
- три оставшихся чанка, N=2: второй и третий не стартуют, пока не вернулся первый (прогрев)
- `--concurrency 0` и `--concurrency 9` — ошибка до LLM
- `--resume` не зовёт LLM для `done`
- два параллельных успеха: оба `done` в `state.json`, оба перевода в EPUB; файл state не порван
- нет `new HttpClient`; три проекта; тесты не ходят в сеть

## Риски

- Provod резервирует оценку стоимости **на каждый in-flight** (`ReservedOutputTokens` × вход). Available = баланс − сумма резервов. N=4 при одном чанке на ~90 ₽ резерва требует ~360 ₽ available; иначе `402`. Документация: баланс и 402 на provod.ai. Дефолт 2 — из-за этого, не из RPM.
- Холодный кеш: N запросов, стартовавших вместе, часто все cache-write. Прогрев одним чанком обязателен.
- `429` / `502` / `503` при ширине >1 чаще; ретраи уже есть, не раздувать MaxRetries «заодно».
- Гонка записи `state.json` — потерять `done`. Один писатель.
- Живой бар эпохи 11 не thread-safe: гонка `StepBegin` без сериализации в Core сломает stderr.
- ETA по сумме шагов завысит стену в N раз, если не делить на ширину пула.
